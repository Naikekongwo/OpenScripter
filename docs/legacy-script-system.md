# 旧脚本系统分析报告

分析对象：`青空.exe`（Kono Aozora ni Yakusoku wo，CK-GAL 系引擎）及其 `Script.pac`、`Script/*.bin`。
材料：`LEGACY/青空.exe.asm`（IDA 全量反汇编）、`LEGACY/青空.exe.map`、反编译得到的 `sub_43A700` 与 `sub_428870` 伪代码、解包后的 `Script/*.bin`。

## 0. 结论摘要

- 剧本按 `PAC` 包分发，包内是连续的 zlib 流，每条流解压后就是一份 `.bin` 剧本。
- `.bin` 是紧凑的「记录数组 + 字符串池」格式：`u32 记录数`，随后每条记录 8 字节，最后是以 NUL 分隔的字符串池。
- 引擎里有两层执行结构：`sub_43A700` 是 41 条指令的栈式 VM，`sub_428870` 是 206 条命令的分发器（命令 ID 0..205）。
- `.bin` 中标签 26 的记录，其操作数高 16 位是参数个数、低 16 位是命令 ID；与 206 条命令表的参数个数逐条吻合。标签 26 因此可判定为「调用命令」。
- 尚未定位 `.bin` 到 VM 程序数组的装载与重编码点，标签 0..37 的完整语义仍是未决项。

## 1. 分析材料与方法

| 材料 | 内容 |
| --- | --- |
| `LEGACY/青空.exe.asm` | IDA 全量反汇编，约 700 万行 |
| `LEGACY/青空.exe.map` | 符号表，用于地址与函数名对照 |

方法：先解析 PE 与文件格式，再用反汇编交叉引用定位加载器和分发器，最后用脚本样本验证字段语义。

## 2. 打包层：PAC

`CK-GAL.pac`、`Script.pac` 等文件的头部为：

```text
50 41 43 00   "PAC\0"
A0 00 00 00   流数量（Script.pac 为 0xA0 = 160）
03 00 00 00   版本或模式
78 9C ...     第一条 zlib 流
```

- 头部之后是**连续的 zlib 流**，没有逐流偏移表；解压一条后，`unused_data` 的起点就是下一条流的开头。
- 对 `Script.pac` 从偏移 12 解压，得到 233845 字节，与 `Effect.bin` 完全一致；该流之后的 `unused_data` 以 `78 9C` 开头，确认为下一条流。
- 因此「一个 `.bin` = 一条 zlib 流」，包本身不改变成员字节。

## 3. 脚本层：.bin

结构：

```text
u32 record_count
record[record_count]   每条 8 字节：{ u32 operand; u32 tag }
string_pool            NUL 分隔的 CP932 字符串，1 基索引
```

验证：四份样本的首字符串偏移都精确等于 `8 + record_count * 8`。

| 文件 | 记录数 | 首字符串偏移 | 文件大小 |
| --- | ---: | ---: | ---: |
| `茜01.bin` | 4520 | 36168 | 47387 |
| `System.bin` | 16164 | 129320 | 132201 |
| `Effect.bin` | 28348 | 226792 | 233845 |
| `プロローグ01.bin` | 28329 | 226640 | 286619 |

除尾部元数据外，第二条字段（标签）在样本中取值 0..37。每份文件的**最后一条记录**是 `(0, 字符串数)`，例如茜01 为 `(0, 359)`，Effect 为 `(0, 499)`，System 为 `(0, 228)`。这条记录是尾部元数据，不是普通指令。

## 4. 运行时 VM：sub_43A700

### 4.1 对象布局

伪代码中的 `this` 是 `CScript`（对象大小 0x14C）：

| 下标 | 偏移 | 含义 |
| ---: | ---: | --- |
| `this[1]` | 0x04 | 变量数组 |
| `this[2]` | 0x08 | 标志数组（标签命中标记） |
| `this[4]` | 0x10 | 程序数组，每条 8 字节 `{opcode, operand}` |
| `this[5]` / `this[6]` | 0x14 / 0x18 | 参数栈 |
| `this[8]` | 0x20 | 辅助栈 |
| `this[11]` | 0x2C | 参数值数组 |
| `this[43]` | 0xAC | 参数类型数组 |
| `this[75]` | 0x12C | 累加器 |
| `this[76]` | 0x130 | 第二操作数 |
| `this[77]` | 0x134 | 程序长度 |
| `this[80]` | 0x140 | 程序计数器 |
| `this[81]` | 0x144 | 当前标签/返回索引 |
| `this[82]` | 0x148 | 条件执行开关 |

取指方式：`record = this[4] + 8 * this[80]`，`opcode = record[0]`，`operand = record[1]`。

## 5. 命令分发器：sub_428870

### 5.1 调用约定

```c
int sub_428870(int cmd, int *args);
```

- `cmd` 取值 0..205，对应 206 个分支。
- `args` 是参数数组；每个参数的类型存在 `CScript + 0xAC`，值存在 `CScript + 0x2C`。
- 分发器开头对每个参数做一次「若类型为字符串则复制到 1KB 缓冲区」的处理（`sub_439630` / `sub_439940`），因此字符串参数最终以固定缓冲区指针的形式传给处理器。
- 处理器集中在 `sub_41Bxxx` 到 `sub_41Fxxx` 区间。

## 7. .bin 与 VM 的衔接

### 7.1 已确认：标签 26 是调用命令

`.bin` 记录的第二字段为 26 时，第一字段是一个打包值：高 16 位为参数个数，低 16 位为命令 ID。逐条核对：

| 记录 | 解包 | 命令表参数个数 | 结果 |
| --- | --- | ---: | --- |
| `(0x10016, 26)` | cmd 22, argc 1 | 1 | 吻合 |
| `(0x2000D, 26)` | cmd 13, argc 2 | 2 | 吻合 |
| `(0x20069, 26)` | cmd 105, argc 2 | 2 | 吻合 |
| `(0x600BC, 26)` | cmd 188, argc 6 | 6 | 吻合 |

这条证据把「标签 26 = 调用命令」从猜测提升为确认，也说明 `.bin` 的语义直接对应 `sub_428870` 的命令表。

### 7.2 推断：标签 0、5、7、24、25

- 标签 0 出现最多，操作数是各种常数（400、200、100、50、20、10、0、位掩码等），最可能是「压入整数/数据」。
- 标签 5 的操作数常落在字符串索引范围内（如 151 指向角色名 `航`），最可能是「压入字符串索引」。
- 标签 7 常出现在调用之后，操作数多为 0，可能是语句/块分隔。
- 标签 24、25 出现在段落边界，可能是块开始/结束。
- 尾部 `(0, 字符串数)` 是元数据。

这些推断的置信度低于标签 26，需要装载器或动态验证来确认。

### 7.3 未决：装载与重编码

VM 的调用指令是 opcode 7，而 `.bin` 的调用标签是 26；两者编号不同，说明中间存在一次装载/重编码：

```text
.bin 记录 {operand, tag}
        |
        v
装载器（未定位）
        |
        v
VM 程序数组 {opcode, operand}
```

可能的形式有两种：

1. **翻译表**：装载器用一张 38 项的映射表把 `.bin` 标签翻译成 VM opcode，标签 26 映射为 7。
2. **不同版本的 VM**：`.bin` 属于另一版引擎的指令集，`青空.exe` 里的 `sub_43A700` 是改写后的表达式 VM，两者共用命令分发器但 opcode 编号不同。

`Script.pac` 的头部字段 `0xA0`（160）与脚本数量一致，但包内没有逐流偏移表；装载器很可能按顺序解压并缓存每份剧本。找到这个函数即可确认重编码方式。

## 8. 对重制脚本格式的启示

1. **命令表可以直接复用**：206 条命令、参数个数、处理器地址是一份现成的语义基线。新格式不必重新发明演出指令。
2. **字符串池独立**：旧格式把台词、资源名、角色名混在一个池里，用 1 基索引引用。新格式可以保留「独立文本表 + 索引」的思路，但应按用途分表（台词/资源/角色），避免 359 个字符串里混着 `BG_*.bmp` 与 `「ん…」`。
3. **调用编码要显式化**：旧格式用 `argc<<16|cmd` 压进一个 32 位字段，参数靠栈传递，可读性差。新格式应把命令名、参数名、参数类型写成显式结构。
4. **文本控制码要建模**：`@v/@o/@s/@n` 目前是字符串内嵌，重制时建议改成结构化字段，或至少保留一份可逆的转义规则。
5. **标签与跳转**：旧引擎用类型码 + ID 查表改写 PC，类型 0x18/0x1A/0x26 各有一套。新格式应统一为命名标签，并明确「进入点/条件跳转/返回」三类语义。

## 9. 下一步

1. 定位 `.bin` 装载器：从 `sub_420370` 与 `sub_43A290` 的调用链继续向下，找「读 `u32 count`、分配 `count*8`、把 `{operand, tag}` 换成 `{tag, operand}`」的函数。
2. 反编译 `sub_4398E0`、`sub_439840`、`sub_439890`、`sub_4397A0`、`sub_4397F0`，确认 0x18/0x1A/0x26 三类标签的跳转语义。
3. 用一份最小剧本（`System.bin` 或 `Effect.bin`）逐条对照命令表，把标签 0..37 的语义补全。
4. 在模拟器里跑通一份剧本，验证「标签 26 + 命令表」的解释是否正确，再决定新格式的字段设计。
